# TSC 论文与源码总结

本轮范围：读论文、对照核心代码、整理研究问题。停止依赖安装、仿真、训练和指标复现。
来源截至 2026-11-02；源码归档不等于运行验证。细节与阅读范围见 RL_READING.md。

## 1. 脉络：究竟用 RL 优化什么？

| 方法 | 训练主线 | 关键监督 | 实际需要分清 |
|---|---|---|---|
| LLMLight / LightGPT | 教师轨迹、critic 过滤、SFT、CGPR 排序 | 交通 Q critic 给候选相位评分 | 主要把强教师/critic 的知识迁入 LLM，并非在线 PPO 直接优化 ATT |
| CoLLMLight | 协同慢推理 SR、快决策 RD；SFT 后 PPO | 仿真最优相位标签、推理长度、自报建议效用 | 模拟异步协同与建议的真实增量收益不同 |
| Traffic-R1 | 离线 GRPO 后在线交通 RL | 专家动作、格式、整轨迹交通回报 | STPO 平均分配轨迹奖励，细粒度交通归因仍弱 |
| OracleTSC | 在线 PPO、value head、GAE | 队列改善、阈值、输出相位一致性 | 一致性不等于动作后果好；证据主要为两个单路口 |
| HeraldLight | 交通预测、教师 SFT、双 LLM 纠错排序 | 预测/规则、语言评价 | 联合相位与时长；不能把语言 critic 当 Q/V critic |
| LA-Light | 工具辅助决策、事件处理 | 感知、辅助策略、解释/评估工具 | 原论文 RL 助手与当前重构版 MP 助手不同 |
| ProcessLight | SFT warm-up、分步过程策略优化 | claim 验证、删步动作分布变化、步骤树优势 | 语言步骤信用不等于跨交通时刻的因果信用 |

TSC 是多步控制任务，但一次 LLM 强化微调样本可能只是“给定状态，输出相位标签”。
需要分别看三个时间轴：语言 token、连续交通决策、多路口传播。

## 2. 最重要的代码发现

CoLLMLight 最值得先读。FTSample 已从快照枚举候选相位、继续多步仿真，产生 Best_Signal。
ppo_ft.py 随后对固定状态生成推理和动作，用是否命中标签计算 ±1，而非每次 PPO 更新在线跑 CityFlow。
SR 的效用 U 来自 RD 的 used_atr 自报；它没有直接测量“同一状态下，有建议比无建议好多少”。

必须纠正此前的宽泛判断：ICLR 最终版已经测试额外一步建议延迟与邻居消息丢失。
“它没考虑过时”和“我们首次加 rollout”都不能成立。代码串行运行推理/动作、用历史输入模拟滞后，
也应与真实后台并发和物理延迟分开描述。

Traffic-R1 确有在线交通反馈，但 STPO 将轨迹奖励按 R_traj/T 平均分给各步。
它降低了长轨迹优化的计算负担，没有精确区分某次决策或某个路口造成的后果。
其公开 checkpoint 较早，完整训练代码和全部数据未公开，不能声称已做官方训练源码审计。

OracleTSC 在环境收益超过 hurdle 时鼓励相位一致性，并非无条件压低文本熵。
其“75% 改善”主要相对未训练 LLM，不能读成比强 RL 改善 75%。
未找到可确认官方实现，因此只分析正文与算法；LibSignal 只是参考环境。

HeraldLight 的提升混合了预测、明确规则、相位/时长动作空间和语言模型训练。
若只比固定时长基线，无法单独证明大模型推理的贡献。

LA-Light 当前工具共享缓存 snapshot，MP 建议可能在调用推荐工具前就已经可见。
主循环完成 LLM 调用后才推进环境，因此 API 等待时间没有自动变成交通延迟。
后续研究工具价值前，要确认工具提供了哪些新增信息。

ProcessLight 已做分步信用分配：验证当前观测中的 claim，删除一步并计算相位分布 JSD，
再用步骤树形成 token 优势。重要性按 prompt 预计算、训练时复用。
它测量的是动作对步骤的敏感性，尚不能等同于步骤带来的交通增益。

## 3. 推荐研究问题

优先问题：**慢建议到达并被执行时，相对当前快策略还有多少实际价值？**

快策略负责每个合法时刻的控制，慢 LLM 提供带时间戳和适用条件的协同建议。
在实际使用状态比较有/无建议的配对后果：

ΔU(s_exec,g) = G_H(with g) - G_H(without g)

仿真分支只在训练时提供标签；部署时由轻量预测器估计增益与误差，选择采用、忽略或刷新。
交通增益与查询成本分别记账，不能用自报“采用了建议”替代效果。
已有 guarded supervision 也研究反事实与门控，因此候选贡献必须落在异步执行时效与跨时间归因，
目前只是一项值得验证的假设，没有确认首创性或效果。

第二条线：在 TransSimHub 的传感器故障/应急事件中研究工具查询的信息价值。
区分空队列、未知和不可用道路；区分旧 snapshot 的视图与真实新增观测。
如果工具没有新增信息，就不能把重复读取描述为有效信息获取。

第三条线：可变时长下的多路口信用分配。按真实秒数累计交通代价，匹配相位/时长空间。
SMDP 本身已有成熟方法；只改时间折扣不足以构成创新，应与异步协同的后果归因结合。

## 4. 代码组织与阅读顺序

vendor/ 保存 10 个方法/环境的原始源码，来源与校验见 sources.lock.json。
OracleTSC 无确认官方方法代码；Traffic-R1 无完整训练实现。缺失部分没有用自编方法替代。

建议先读 CoLLMLight 的 FTSample.py、ppo_ft.py、CoLLMlight.py 和 CoLLMLightAgent.py；
再对照 LLMTSCS 的 critic/SFT/CGPR、ProcessLight 的 rewards/advantage；
最后读 LA-Light 的 tools/agent/runtime 与事件配置。
详细入口见 CODE_INDEX.md，候选设计和失败条件见 IDEAS.md。

GENEX-TSC、VLALight 本轮仅归档，未计入精读结论。
